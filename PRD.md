# WikiLive: живые таблицы в тексте

## Описание для хакатона

Создай модуль живой вики-системы, где текст и таблицы становятся единым инструментом для совместной работы и управления знаниями.

**Целевая аудитория:** фронтенд-разработчики, бэкенд-разработчики, UX/UI-дизайнеры, менеджеры по продукту.

| Термин | Пояснение |
|--------|-----------|
| Фронтенд-разработчики | разработчики пользовательского интерфейса |
| UX/UI | пользовательский опыт / пользовательский интерфейс |

## Условие задачи для хакатона

### Проблематика

Корпоративные знания часто разрознены: таблицы живут отдельно от документации, а страницы не связаны между собой. Текущий редактор страниц — это просто текст с минимальным форматированием, чего недостаточно для полноценной базы знаний. Пользователям приходится переключаться между разными инструментами, терять контекст и вручную поддерживать актуальность данных. Нужен единый модуль, в котором страницы, таблицы и связи между сущностями становятся частью одного рабочего пространства.

### Полное описание

В рамках кейса команде необходимо спроектировать и реализовать модуль вики-редактора для MWS Tables, в котором текстовые страницы перестают быть изолированными документами и становятся рабочими узлами знаний.

**Базовый сценарий:** пользователь создаёт или редактирует страницу, вставляет в неё существующую таблицу из MWS Tables, дополняет страницу текстом, быстро добавляет блоки через slash-menu с поддержкой горячих клавиш и связывает страницу с другими страницами через ссылки и обратные ссылки. При редактировании контент автосохраняется по ходу ввода (in-line), дублируется в локальном кэше браузера и синхронизируется с бэкендом.

Ожидается не просто текстовый редактор, а решение, которое приближает MWS Tables к роли рабочей knowledge-платформы. Таблицы должны восприниматься пользователем как часть содержимого страницы, а не как внешний объект, на который дана ссылка. Пользователю должно быть удобно работать с контентом, находить связи между страницами, не терять правки при сбоях и перезагрузке и совместно редактировать материал. Дополнительные возможности, такие как комментирование, версионирование, AI-подсказки, граф связей, плагины и встраивание внешних элементов, могут существенно усилить решение, если они логично встроены в продуктовый сценарий.

Особое внимание в кейсе уделяется интеграциям и UX. Хорошее решение должно быть похоже на модуль, который можно легко вставить в существующий продуктовый интерфейс без изменений MWS Tables, и визуально / по компонентам опираться на предоставленный Design Kit. Важно показать не только богатство редактора, но и то, как он живёт рядом с реальными таблицами, страницами и API платформы.

### Технические ограничения

- Решение должно быть ориентировано на интеграцию с MWS Tables через API с максимальным покрытием функций.
- Вставка существующей таблицы MWS Tables в тело страницы, in-line автосохранение локальное и синхронизация, обратные ссылки, slash-menu с поддержкой горячих клавиш являются обязательной функцией.
- Совместная работа над документом должна быть реализована в любом проверяемом виде.
- Рекомендуемый стек: React + Java. Допустим альтернативный стек, если команда может обосновать интеграцию и воспроизводимо показать работу решения.
- Базовый редактор должен опираться на open-source решение с понятной лицензией. Предпочтительны permissive license / MIT-like варианты.
- Если используются AI-функции, необходимо явно указать их зависимости, ограничения и сценарии применения.
- Дополнительные функции не компенсируют отсутствие обязательного контура.

### Критерии оценки

| № | Критерий | Баллы | Что проверяют |
|---|----------|-------|---------------|
| 1 | Обязательная функциональность и работоспособность | 0–25 | Наличие и стабильная работа обязательных функций: вставка таблицы, in-line сохранение, backlinks, slash-menu с поддержкой горячих клавиш, совместная работа. |
| 2 | Интеграция с MWS Tables и качество данных | 0–25 | Насколько результативно решение интегрируется с таблицами, страницами и API продукта. Высоко оцениваются сценарии, где таблица внутри страницы остаётся живым объектом, а не статичным. |
| 3 | Пользовательский опыт и качество интерфейса | 0–25 | Удобство работы со страницей, навигацией, вставкой блоков, поиском связей и редактированием. В плюс — аккуратный UX, понятная структура, скорость базовых действий и чистота интерфейса, соответствие Design Kit. |
| 4 | Глубина проработки дополнительного функционала | 0–25 | Версионирование, комментарии, граф связей, AI-помощь, плагины и другие расширения — если обоснованы и усиливают сценарии взаимодействия. |

## Что сдаётся на проверку

Детали по каждой части — на соответствующей странице задачи.

- Открытый репозиторий с кодом и инструкцией по запуску. Желательно Docker / docker-compose и **однострочный** запуск всего решения; при проблемах с запуском решение может не рассматриваться дальше.
- Схема компонентов редактора и интеграций.
- Заполненный шаблон обязательных и дополнительных фич и способы реализации.
- Демо-видео.
- Презентация: сценарий, UX-логика, возможности развития.

Каждый артефакт — в соответствующую вкладку задачи; иначе решение не допускают к проверке жюри.
